深层诊断：根本性设计问题

上一轮列出了15个代码层面的问题。以下是从设计/架构角度发现的4个根本性缺陷。

根因 1：两套完全独立的渲染引擎

Living Space 主页面和 Void Chat 对话页各自实现了一套完整的星空渲染系统，零代码共享：

Living Space 主页（background.ts + constellation.ts）

• Chunk 系统，每 Chunk 800 星

• 8 星云 + 银河带

• 流星系统（3 种类型）

• Void Gate 点火粒子系统

• Whisper 轨迹系统

• Fragment 星体 4 层光晕

• 力量导向布局引擎

• 连线使用语义颜色（群组色）

Void Chat 页面（StarBackground + Constellation）

• 固定 3300 星（3 层视差）

• 6 星云，颜色少了金色

• 无流星系统

• 无点火/Whisper

• Fragment 星体只有 2 层光晕

• 无布局引擎

• 连线颜色硬编码（紫-粉-蓝）

后果：两个页面的视觉质量天然不一致。主页更丰富（4层光晕、语义颜色），Void 页更扁平（2层光晕、硬编码颜色）。每次视觉改进都要在 2 处重复实现。

根因 2：Canvas 没有设计系统

CSS 有 :root 变量定义颜色主题，但所有 Canvas 渲染代码使用原始 rgba() 硬编码值，散落在 6+ 个文件中。

颜色文件硬编码位置
背景黑3 个文件#04040a / #06060e / #0a0a0f (3 个不同值)
星云色2 个文件StarBackground 少一个金色，LivingSpace 有金色
连线色2 个文件主页用语义颜色，Void 硬编码紫-粉-蓝
Cross Flare4 处定义3 处有效（含1处死代码），2 种不同公式
Vignette2 个文件Opacity 值不一致（0.55 vs 0.70）
CSS 变量4 个组件每个组件用自己的 :root 重复定义（Svelte 不 scoped）

后果：整个项目的色彩一致性纯靠人工记忆维护。改了 app.css 的颜色变量不影响 Canvas 渲染，改了背景星的颜色不影响连接线。

根因 3：动画缺乏叙事动机

当前所有动画都是纯装饰性的、无差别的循环脉冲。不同元素以不同的、无关联的频率闪烁：

  • Connection line pulse: sin(time * 0.8) — 约 1.3s 周期
  • Energy dot pulse: sin(time * 2.5) — 约 2.5s 周期
  • Star breath: sin(time * 0.5) — 约 12.6s 周期
  • Unread star pulse: sin(time * 2.5) — 约 2.5s 周期
  • Cross flare pulse: sin(time * 1.5) — 约 4.2s 周期
  • 开场文本逐字显示: 1 秒/字
  • Whispers: 独立时间线
  • Ignition: 独立时间线
  • Fragment emergence: hidden→emerging(1.2s)→lingering(3.5s)→crystallizing(1s)→star

9 种不同的时间参数，各自独立运行，没有统一的节奏编排。好的动效设计应该用动画讲故事、引导注意力，而非让一切同时闪烁。

根因 4：缺乏视觉层级和焦点引导

所有 16 个 Fragment 星体在视觉上完全平等——相同的 4 层光晕渲染、相同的默认大小（4.5±0.5）、相同的呼吸动画。用户打开页面看到一片星海，但没有任何线索告诉 ta 该看哪里、什么重要。

对比优秀案例：

  • Apple 的页面会用 大小、亮度、位置 逐层引导视线
  • 游戏 UI 会用 高亮、运动、对比度 指向当前焦点
  • 数据可视化会用 颜色饱和度、尺寸编码 区分数据重要性

当前项目：所有星体同等对待，观众视线在画面上随机游走。

总结：问题金字塔

从表到里的问题层级：

表层：颜色不一致、连接线油腻、动画杂乱

中层：两套渲染引擎各玩各的、Canvas 无设计系统

深层：动画缺乏叙事动机、视觉层级缺失

先解决"两套引擎"问题

统一 Living Space 和 Void Chat 的渲染系统，消除代码重复，确保视觉一致

C

设计有时间线的、有引导性的动画编排，让动效为叙事服务
